1. 解析の規則（parse_v2.js）
 v0.5 §1 の本文を収録した（r1）。変更は、参照番号の更新（§5 の表 → §11 の表）だけ。
【正規化】
 N-1 全角の［ ］：を半角の [ ] : に1文字ずつ置き換える（位置は変わらない）。値の中の全角コロンも半角になる（版A・B と同じ）。
 N-2 見本値の比較だけ: Unicode NFKC、前後の空白を除く、連続する空白・改行を1つの空白にする。位置の計算には使わない。
 N-3 タグ名・キー名は大文字小文字を区別しない。返すキー名は大文字。

【第1段階 候補】
 S1-1 開始タグは "[TAG]" の完全一致。"[ TAG ]" や属性付きはタグではない。
 S1-2 開始タグの出現位置をすべて候補にする。ID は出現順に c1, c2, …
 S1-3 本文は開始タグの直後から、次の閉じタグ "[/TAG]" が次の開始タグより前にあればその直前まで（閉じあり）。
      そうでなければ次の開始タグの直前、または文末まで（閉じなし）。前に開始タグの無い閉じタグは無視する。
 S1-4 位置: start＝開始タグの位置、end＝本文の終わり（含まない）。JavaScript の文字列位置（UTF-16 の単位）、正規化前の原文の位置。

【第2段階 候補ごとの判定】
 S2-1 項目の取り出し（キーの認識）: キーをテンプレート順に走査し、行頭の出現を優先する。行がつながっていても読む（1行形式）。
      値は次のキーの直前まで（前後の空白を除く）。値の途中の「キー名:」は、行頭でなければキーとも区切りとも扱わない（D11）。
 S2-2 重複: 同じキーが行頭に2回以上あれば重複（大文字小文字を区別しない）。値は位置が最も前の出現を採用（D7）。
      後の出現は値の区切りとして扱い、その値が最初の値と違えば conflicts にキーを入れる。
      1行形式の中の重複は検出しない（D11 の既知の制約。後の出現は前の値に含まれる）。
 S2-3 キー種類数 ＜ 3 → NOT_STRUCTURAL（D1）
 S2-4 識別キー以外のキーが1つも無い → NO_CONTENT（D10）
 S2-5 見本値（キーごと）: TEMPLATE＝§11 の表（v0.5 では §5）の文言と N-2 の後で完全一致／PARENTHESIZED＝値全体が ( ) か （ ） で囲まれている。
      TEMPLATE を優先。識別キーにも付ける（ただし候補を外す判定には識別キーを使わない）。
 S2-6 識別キー以外の値が全部見本値 → TEMPLATE（D4）。それ以外 → 有効

【第3段階 採用または失敗】判定の順番どおりに適用する
 S3-1 候補が0件 → null（NO_BLOCK）
 S3-2 有効な候補が2件以上 → PARSE_FAILED / AMBIGUOUS_MULTIPLE_BLOCKS（D2）
 S3-3 有効な候補が0件 → PARSE_FAILED。理由は、TEMPLATE があれば TEMPLATE_ONLY、なければ NO_CONTENT があれば NO_CONTENT_FIELDS、
      それもなければ NO_STRUCTURAL_CANDIDATE
 S3-4 有効な候補が1件で、閉じなし、かつ後ろに別の候補がある → PARSE_FAILED / UNCLOSED_FOLLOWED_BY_TAG
 S3-5 それ以外は採用。閉じなし（文末まで）→ UNCONFIRMED ＋ 警告 UNCLOSED（D3）。不足キーあり → PARTIAL。なし → OK
 S3-6 理由の優先順（複数当てはまるとき）: AMBIGUOUS_MULTIPLE_BLOCKS ＞ UNCLOSED_FOLLOWED_BY_TAG ＞ TEMPLATE_ONLY ＞ NO_CONTENT_FIELDS ＞ NO_STRUCTURAL_CANDIDATE
 S3-7 未知のラベル（採用した候補の本文のみ）: 行頭の「空白・: ・[ ・] ・/ を含まない1〜40文字＋コロン」でキー集合に無いもの。
      数字だけ（例 12:30）と、コロンの直後が / のもの（URL）は除く。見つかれば UNRECOGNIZED_LABEL:<ラベル> と CLASSIFICATION_UNCERTAIN。値の切り方は変えない。

4. 受信1回の処理（契約 v0.3 §2 を実装に合わせて確定）
 R-1 まず parseAttempts に1件追記する。中身：attemptId、受信時刻、経路、原文、原文の SHA-256、3種のタグの解析結果、ruleVersion、テンプレート表の版、依頼した Task ID（中継・API のとき）。
 R-1a（r1。C45）原文の SHA-256 は、計算できる環境（localhost・https の Web Crypto）では記録する。計算できないときは null として記録し、受信は止めない。原文そのものは必ず保存する。
 R-2（D12=A）SYNTHESIS → DONE → RESULT の順で、採用できる結果を持つ最初のタグを picked にする。他の採用できるタグは notAdopted に残す。
 R-3 どのタグも採用できず PARSE_FAILED がある → 記録だけ（failed）。既存の採用・改訂番号は変えない。
 R-4 3種とも null → 形式外。観測なら NO_BLOCK として採用できる。統合・完了には採用しない。
 R-5 宛先：返事の TASK が「今の世代」の Task ID と一致 → その Task。観測で TASK が無ければ FROM で決めるのは、その観測の世代が1のときだけ。
 R-6 宛先不明 → 未割り当て。人が宛先を選ぶと、同じ試行に割り当てを追記する（新しい試行は作らない）。
     ・1つの試行は1回だけ割り当てられる
     ・割り当て先は今の世代の Task に限る
     ・割り当てだけでは、確認・GATE・統合は起きない
 R-7（新。C39・C40）手動の割り当ても D12 を迂回できない。
     ・picked がある試行は、その種類にしか割り当てられない
     ・picked が無いのに採用できるタグがある記録（編集・不整合な JSON からしか生じない）は、割り当てを拒否する
 R-8（新。C39）古い NEXT への完了報告は採用しない（outcome 'stale'。記録には残る）。
 R-9 遅れた返事（古い世代の Task への返事）は 'late' として記録し、採用しない。

5. 採用の規則（D13=A）
 A-1 採用できる結果：OK・PARTIAL・UNCONFIRMED・NO_BLOCK（観測のみ）。
 A-2 NO_BLOCK の保存形：{ status:'NO_BLOCK', reason:null, fields:{}, missing:<RESULT の全キー>, warnings:[], conflicts:[], selected:null, candidates:[], … }
 A-3 新しい受信が割り当てられたら、自動で採用を切り替える。ただし次の場合は切り替えない：
     ・採用できない（PARSE_FAILED・null）
     ・NO_BLOCK で、採用中が構造化された結果か旧形式（'kept'）
     ・TASK が今の世代でない
 A-4 確認は試行ごと。切り替えた新しい試行は未確認から始まる。

6. 世代
 G-1（契約 v0.3 から変更）Task ID：
     ・世代1は旧形式の ID のまま："<Case>-OBS-<AI名>"・"<Case>-SYN"・"<Case>-NEXT"
     ・世代2以上は "-<n>" を付ける
     ・旧 Case と新 Case で ID が一致する（1b I-1）
 G-2 観測の「作り直して再送」、統合のやり直し、NEXT の送り直しのたびに世代を上げる。
     統合のやり直しと NEXT の新しい世代では、前の統合・GATE・NEXT・DONE を保管庫（archive）へ移す（消さない）。
 G-3 返事の TASK が今の世代でない → 採用しない（R-9）。
 G-4 TASK が無い返事は、その Task の世代が1のときだけ今の世代とみなす。
 G-5 中継・API の回収と取り込みは、依頼時に発行した Task ID で行う（§10）。

7. 改訂番号と失効
 V-1 obsRevision と synRevision は増えるだけで、戻らない。
     ・obsRevision は観測の採用の切り替え、観測への確認・取り消しで上がる
     ・synRevision は統合の採用の切り替え、統合への確認・取り消しで上がる
     ・統合の依頼の後に届いた観測（遅れて利用可能になった観測を含む）でも obsRevision は上がるので、統合は古くなる（1b I-3：既存 Studio からの動作の変化）
 V-2 参照：
     ・統合依頼：{ task, gen, obsRevision, inputAttemptIds }
     ・GATE：{ id, decision, reason, synthesisAttemptId, synRevision }
     ・NEXT：{ id, task, gen, gateId, packet }
     ・DONE：{ attemptId, nextTask }
 V-3 古いかどうかは、その場で計算する（保存しない）。
     ・統合が古い：統合依頼の改訂番号が今と違う、または統合依頼が今の世代でない
     ・GATE が古い：統合が古い、または判断した統合・改訂番号が今と違う、または今の統合が利用可能でない
     ・NEXT が古い：GATE が古い、または NEXT が今の GATE に結び付いていない
     ・DONE が古い：NEXT が古い、または DONE が今の NEXT への報告でない
 V-4 ガードは canRequestSynthesis・canGate・canSendNext・canCountDone に集約する。画面・操作・nextStep・send・回収のすべてがこれを使う。
 V-5 古いものは消さない。画面と書き出しに「古い（理由）」を出す。

8. 確認と取り消し
 K-1 確認の記録は追記のみ：{ eventId, attemptId, item, action:'confirm'|'revoke', at, by }。by は画面の操作記録で、本人確認ではない。
 K-2 確認の状態は、各項目の最後の記録で決まる。
 K-3 確認・取り消しは、その試行が採用中なら改訂番号を上げる。
 K-4 AI の本文に「確認済み」「承認」「APPROVE」とあっても、確認・GATE は変わらない。

9. 依頼記録（段階1c。D15）
 Q-1 依頼文（観測・統合・NEXT）は、作るたびに Case の追記専用の記録 requests に1件保存する。
     中身：requestId、kind（OBS／SYN／NEXT）、name、task、gen、packet（本文）、sha256、at、deliveries。
     この記録がこのブラウザに保存できない限り、送付しない（Q-1a。C42）。
     本文の SHA-256 は、計算できないときは null として記録し、送付は止めない（R-1a と同じ。本文そのものは必ず保存する）（r1。C45）。
 Q-2 送付のたびに、送付結果を同じ記録の deliveries に追記する。
     中身：at、status（copied／shown／queued／answered／failed）、connector、error、retry、route（中継のときの経路）、toFile・fromFile（中継が agent 経路で実際に書いた依頼ファイルと、返事を待つ結果ファイル。段階1d-B）。
     ・送付済み（delivered）＝ copied・shown・queued・answered のどれかが1回以上ある
     ・失敗（failed）＝ 送付済みがなく、failed がある
     ・未送付（unsent）＝ どちらもない
 Q-3 送り直し：
     ・今の依頼（今の Task ID の最新の記録）が failed のときだけ、同じ Task ID・同じ本文で送り直せる
     ・送り直しでは世代を上げない
     ・初回の観測送付が失敗していれば、「送る」も送り直しとして扱う
 Q-4 再表示・再コピー：
     ・「依頼文を表示」は保存済みの本文そのものを出す。作り直さない
     ・再コピーで変わるのは、ログとコピー回数だけ
     ・本文が保存されていない旧 Case では「保存されていません」と表示する（旧 NEXT は c.next.packet を表示）
 Q-5 状態の付け方：送付が成功したとき、観測・統合依頼・NEXT に送付状態を付けるのは、記録の Task ID が今の Task ID と一致するときだけ（C42 (B)）。
 Q-6 二重送付の防止（D16。C43・C44）：
     ・同じ依頼 ID の送付中、および同じ Case・Task の初回観測依頼の準備中・送付中は、次の操作を受け付けない
     ・印は、成功・失敗・保存失敗・例外のどの経路でも外す
     ・送付中のボタンは「送付中…」になり、押せない
 Q-7 読むだけでは Case を書き換えない。旧 Case に requests を足さない。

10. 中継（ローカル中継）からの回収
 W-1 回収は、今の世代の Task ID だけで行う。古い NEXT は回収しない。旧形式で採用済みの観測（attemptId なし）も回収しない。
 W-2 回収を続けるのは、その Task で「タグ付きのブロック（picked あり）」が採用されるまで（D14）。
     失敗・遅着・NO_BLOCK の後も続ける。同じ原文は二重に記録しない。
 W-3 回収は1つずつ順に実行する（タイマーと手動ボタンが重なっても、同じ原文を二重に記録しない。C40 (a)）。
 W-4 中継は 127.0.0.1 だけで待ち受ける。
     ・agent 経路：exchange/<CASE>/<TASK>/ に to-<AI>.md を書き、AI が書いた from-<AI>.md を回収する。AI を起動する仕組みはない。/task の応答で、書いた to- と、返事を待つ from- の完全なパス（toFile・fromFile）を返す（段階1d-B）
     ・API 経路：中継がサーバー側で API を呼ぶ
 W-5（段階1d-B）agent 経路の依頼が返事を待っている間（観測の行・統合待ち・完了報告待ち）、画面に「AIへの指示を表示」を出す。
     ・表示するのは、§13 S-3 の指示文（依頼ファイルと結果ファイルの完全なパス、書いてよいのは結果ファイルだけ、合わないときは止まる）
     ・案内を出すかどうかとパスは、今の設定ではなく、今の依頼の最後の送付の記録で決める（Codex C51）：送付の経路が agent のときだけ出す。パスは、中継が返した toFile・fromFile を使う
     ・中継がパスを返さない（古い中継）ときだけ、§13 S-3 で推定し、「推定」と明示する。推定に使う受け渡しフォルダは、同じ中継 URL で「接続を確認」したときに記録したもの（settings.exchangeDir と exchangeFor）。中継 URL を変えたとき・確認に失敗したときは記録を消す。分からなければ中継からの相対パス

A. 受け入れ済みの制約（変えない）
 解析の制約（v0.5 §6 を収録。r1）：
 ・短い本物（識別キー以外が全部括弧）は TEMPLATE_ONLY になる（D4、N-12）
 ・キー2種類以下の短い本物は NOT_STRUCTURAL になる（D1、N-09）
 ・値の途中のタグ文字列は、候補の切り方を乱す（D5、N-07・N-14）。入れ子・交差したタグも同様（N-16）。コードフェンスは特別扱いしない
 ・1行形式の中の重複は検出しない（D11、R-07）
 ・同じ回答を引用と本物で二重に含む返事は AMBIGUOUS になり、再送が必要（D2）
 ・形式外由来の内容を統合AIが正しく示す保証はない。最終確認は GATE の人（D9）
 ・1タブ運用が前提：送付中の印、回収の順番待ち、保存は、タブの間で調整しない。
 ・保存できない状態では送付できない（Q-1a）。保存停止中は JSON の読み込みで保存を再開する。
 ・依頼文を作り直した文は、元の依頼文の代わりにならない（Q-4）。
 ・中継は AI を起動しない。人が AI に「to- を読み from- を書く」と伝える。

B. 未検証
 ・URL の中の ASCII 以外の文字（例：日本語のままの URL）は、その手前で URL を切る（§13 S-1）。ブラウザのアドレス欄からのコピーは通常、符号化されているので影響しない見込み（推測）。
 ・API 経路（キーなし）。副作用の後に失敗すると、送り直しで重複処理になり得る（C42）。有効にする前に扱いを決める。
 ・mock 経路は「-SYN」で終わる Task だけを統合と見なす（-SYN-2 に観測形式を返す）。中継側の既存の制限。
 ・送付失敗→送り直しを、実際の AI で人が操作する試験：T-LOOP 003 で行う。
 ・Claude Code の別セッションによる、ファイル受け渡しの実接続。
 ・別の環境での再現。
 ・クリップボードの上書きと、AI に貼った本文の一致（記録に残らない）。
