## 1. 守ること

1. **中継の記録が正本**。画面が持つ Case は、中継から読んだ版（rev・sha256）と、その上に足したまだ送っていない編集だけ。
2. **送る前に保存する（Q-1 の引き継ぎ）**：AI へ依頼を送る前に、その依頼文を含む Case の書き込みが中継から 200 で返っていなければ送らない。今の `save()` は同期で成否が決まるが、3-B では「中継が受け取った」ことを待つ。
3. **版がぶつかっても混ぜない・上書きしない**（3-A §8-4）：409 `version_conflict` のとき、画面の選択肢は「最新を読み直す」だけ。自分の編集は控え（§3）から見られ、JSON で書き出せる。強制上書きは置かない。
4. **答えが届かなかった書き込みは、同じ requestId・同じ中身で送り直す**。新しい編集は、その送り直しが 200 になった後に、次の書き込みとして送る。そのために、**Pending は控え（§3）に書けてから送る**（D-9）。成否は中継の答えで決め、画面が rev を比べて先回りに決めない（§4.3）。
5. **中継に届かないときは保存できないことを大きく出す**。その間は編集を止める（§5、D-2）。
6. ブラウザの保存領域は**控え**：中継に届かないときの未送信の編集、今開いている Case（`currentId`）、中継の URL。正本としては使わない。

## 2. 画面が持つ状態

```
store = {
  version: 2,                       // 3-B の形（今は 1）
  cases: { id: case },              // 中継から読んだ版＋未送信の編集
  order: [id, …],                   // 中継の一覧の順（3-A §2.2）
  currentId,                        // ブラウザごと（保存領域に残す）
  settings: { … },                  // §6
  meta: { id: { rev, sha256, pending: null | Pending, state } }   // Case ごと（設定は '_settings'。§6）
}
ui = {
  load:  'loading' | 'loaded' | 'loadFailed',   // 起動の読み込み（§4.3）
  relay: 'online' | 'offline',                   // 中継に届くか（§2.2）
  cache: 'ok' | 'failed',                        // 控えに書けるか（§3）
  notSent: { id: [{ task, at, why }] }           // Q-1 で送らなかった依頼（§4.2。Case には書かない）
}
canWrite = ui.load === 'loaded' && ui.relay === 'online' && ui.cache === 'ok'   // §2.3
Pending = { requestId, baseRev, body, sha256Local?, since, tries }
state   = 'clean' | 'dirty' | 'sending' | 'unanswered' | 'conflict' | 'corrupt'
```

- `store.rev`（記録全体の版）は**やめる**。画面の「この記録：…r429」の表示は「記録の口・Case n 件（中継 <URL>）」に替え、今開いている Case の rev を Case の見出しに出す。
- 2-C の写し（`/snapshot`）の rev は、記録の口では使わない（§7、D-3）。

### 2.1 Case ごとの状態の移り変わり

| 今 | できごと | 次 |
|---|---|---|
| clean | 画面で編集 | dirty（書き込みを予約、§4.1） |
| dirty | 予約の時刻（最後の編集から 1 秒） | sending（Pending を作る：新しい requestId、baseRev＝今の rev、body＝その時点の Case の写し） |
| sending | 200（`replayed` を含む） | 控えの Pending を消す。送っている間の編集がなければ clean、あれば §2.4（次の書き込みか conflict） |
| sending | 届かない・時間切れ・5xx・503 `busy` | unanswered（Pending はそのまま）。**`ui.relay` を offline にする**（§2.2） |
| unanswered | `resume()` の 4 に来た（中継に届くようになった・利用者が「送り直す」を押した。§2.3） | sending（**同じ** Pending を送る） |
| sending | 409 `version_conflict` | conflict（§4.4） |
| sending | 409 `record_corrupt` | corrupt（読むだけ。§4.5） |
| sending | 409 `request_id_reused` | 起きないはず。conflict と同じに扱い、ログに残す |
| sending | 400・413・415 | 送れない編集。dirty に戻さず止め、内容を大きく出す（不具合として扱う） |

- 1 つの Case について、中継へ同時に出ている書き込みは**最大 1 つ**。
- `sending` の間にした編集は Case に入るが、Pending の body には入らない（次の書き込みになる）。この編集ができるのは `canWrite` が真の間だけ（§2.3）。
- `dirty` から `sending` に移る前に、Pending を控えに書く（D-9）。書けなければ送らず `dirty` のまま、`ui.cache` を failed にする（§3）。
- 設定（`_settings`）も同じ表で動く（§6）。

### 2.2 中継に届くか（`ui.relay`）

- **online → offline**：どれかの書き込みが「届かない・時間切れ・5xx・503 `busy`」になったとき、または §4.7 の一覧の読み直しが届かなかったとき。
- **offline の間**：どの Case も設定も編集できない（読むだけ。D-2）。offline になる**前**にした編集（dirty・sending 中の編集）は Case と控えの drafts に残る。新しい Case は作れない。依頼は送らない。
- **offline → online**：15 秒ごとに `GET /record` を試し、届いたら online にして、§2.3 の `resume()` を呼ぶ。
- 503 `busy`（ロックが取れない）も、ここでは「届かない」と同じに扱う（同じ Pending を送り直すので安全）。

### 2.3 書けるかどうか（`canWrite`）と戻るときの手順（再監査の指摘1）

止める条件は 3 つ（`ui.load`・`ui.relay`・`ui.cache`）あり、別々に起きて別々に戻る。重なったときの順を決めるため、**1 つの条件と 1 つの手順**にまとめる。

- `canWrite` が真のときだけ、次のことができる：編集・新しい Case・JSON の読み込み・書庫から戻す・設定の編集・中継への書き込み（Pending の送信と送り直しを含む）・AI への依頼の送付。
- `canWrite` が偽の間は、どれもしない。画面は読むだけになり、偽にしている条件をすべて帯に出す（例：「中継に届きません」「控えに書けません」を両方）。送信の予約（dirty）は残し、送らずに待つ。
- **手動の「読み直す」（3 回目の監査の指摘2）**：帯の「読み直す」は、押されたらその場で `GET /record` を 1 回試す（15 秒ごとの確かめを待たない）。届けば `ui.relay` を online にして `resume()` を呼ぶ。届かなければ offline のまま「まだ中継に届きません（hh:mm:ss に確かめました）」と出す。控えが failed のときは、その場で控えに書けるかも 1 回試す。15 秒・30 秒ごとの確かめは、手動とは別にそのまま続く。
- 3 つの条件のどれかがよい方に変わったとき（控えに書けた・中継に届いた）は、必ず `resume()` を呼ぶ。`resume()` は次を上から順に見て、最初に当てはまったところで止まる。
  1. `ui.relay` が offline → 何もしない（§2.2 の 15 秒ごとの確かめに任せる）。読み込みも書き込みもできないため。
  2. `ui.load` が 'loaded' でない → §4.3 の読み込みを **`GET /record` から**始め直す（'loading' に戻す）。読み込みは中継にも控えにも書かないので、`ui.cache` が failed でも行う。読み込みが終われば `resume()` をもう一度呼ぶ。
  3. `ui.cache` が failed → 何もしない（§3 の 30 秒ごとの確かめに任せる）。読み込んだ Case は読むだけで見える。
  4. ここまで来たら `canWrite` は真。§4.3-5 の送り直し → §2.4 の drafts の順に、Case ごとに送る（設定も同じ）。
- 起動時は、`resume()` を呼ぶところから始まる（中継に届かなければ 1 で止まり、届けば 2 で読み込む）。読み込みの途中で中継に届かなくなれば 'loadFailed'・offline（§4.3-3）。
- `resume()` は同時に 2 つ走らせない（走っている間に呼ばれたら、終わった後にもう一度だけ走らせる）。

### 2.4 送り直しが通った後の drafts（再監査の指摘3）

Pending の答えが 200 になったとき、その Case に Pending の後の編集（drafts、dirty）が**あるかないか**で分ける。答えは `{ rev, sha256, replayed?, currentRev? }`（3-A §3.1-4。`currentRev` は replayed のときだけ）。

- **drafts がない**：`meta.rev`・`sha256` を答えの値にし、clean。replayed で `currentRev` が `rev` より大きければ、その後に別の画面が書いているので、その Case を中継から読み直す（clean なので失うものはない）。
- **drafts がある**：画面の Case（drafts の中身）は**置き換えない**。
  - 200（replayed でない）、または replayed で `currentRev` が `rev` と同じ → 土台の版は自分の書き込み。`meta.rev` を答えの `rev` にし、drafts を **baseRev＝その rev** の次の書き込みとして送る（新しい requestId）。
  - replayed で `currentRev` が `rev` より大きい → 自分の書き込みの後に別の画面が書いた。drafts は自分の古い版の上の編集なので、**送らずに conflict**（§4.4）。drafts は控えに残し、「最新を読み直す」で中継の今の版を見せる。`baseRev` を `currentRev` に上げて送ることは**しない**（別の画面の編集を黙って上書きするため）。
- §4.3-5（起動時）と §2.2（戻ったとき）の両方がこの決まりに従う。

## 3. 控え（ブラウザの保存領域）

- キー：`ats-operational-001-3b`（今の `ats-operational-001` とは別。3-B の画面が今の記録を書き換えない）。
- 中身：`{ format: 'ats-ui-cache-1', relay, currentId, pending: { id: Pending }, drafts: { id: { baseRev, case } }, notSent: { id: [...] } }`
  - `pending`：unanswered・sending の Pending（送り直しに使う）。
  - `drafts`：dirty・conflict の Case の、まだ中継にない内容（conflict のとき「自分の編集を見る」に使う）。`baseRev` は、その編集の土台になった版の rev（§2.4・§4.3-6）。Pending があるときは Pending の baseRev＋1。
  - `notSent`：Q-1 で送らなかった依頼（§4.2）。
  - clean の Case の本体は控えに置かない（正本は中継。保存領域の大きさの心配もなくなる）。
- 控えは編集のたびに同期で書く。
- **Pending は控えに書けてから送る（D-9）**。書いた後に読み戻して requestId と body の sha256 が同じことを確かめてから `POST` する。書けなければその書き込みは送らず、`ui.cache` を failed にして、大きな帯で「控えに書けないため保存できません。保存していない編集を JSON で書き出してください」と出す（下の逃がし先）。failed の間は編集を止め（読むだけ）、依頼も送らない。30 秒ごとに控えに書けるか試し、書けたら ok に戻して送る。
  - 理由：控えに残っていない Pending は、答えが届かないままページが閉じると同じ requestId で送り直せず、§1-4 を守れない。控えには clean の Case の本体を置かないので、ふつうは小さい（11/8 の最大の Case 398 KB。上限 5,242,880 字）。
- drafts（編集の中身）が書けないときも同じに扱う（自分の編集が失われうるため）。
- **控えに書けないときの逃がし先（再監査の指摘2）**：書けなかった編集は、画面のメモリの中の Case にだけある。帯に「この画面を閉じると、保存していない編集が失われます」と出し、**「保存していない編集を JSON で書き出す」**を置く。書き出しはブラウザのダウンロードで行い、保存領域を使わないので、控えに書けないときも使える。中身は dirty・conflict の Case ごとの `ats-operational-case`（version 1。§4.6 の JSON の読み込みで戻せる形）。ページを閉じる前に書き出さなければ失われる（3-B の限り。LIMITATIONS に書く）。
  - **送っていない依頼も入れる（3 回目の監査の指摘1）**：書き出す JSON の一番外に `notSent: [{ task, at, why }]`（その Case の `ui.notSent[id]`）を足す。`case` の中には入れない（Case に書かない、D-12）。§4.6 の JSON の読み込みは、`notSent` があれば `ui.notSent[id]` に戻し（同じ `task` は重ねない）、控えに書ければ控えにも書く。004 の画面と今の `parseCaseExport` は外側の知らない項目を読まずに捨てるので、004 で読み込んでも壊れない（`notSent` が消えるだけ）。
  - `notSent` のない JSON を読み込んだときも、依頼文があって送付の記録がない依頼は、今の `StudioState.deliveryLabel` のとおり「未送付」と出る（理由は出ない）。
- 起動時に控えに Pending があれば、全件を読んだ後、同じ Pending をそのまま送り直す（§4.3）。

## 4. 口の使い方

### 4.1 書き込みの予約と送信

- 今の `save()` の 25 か所は、`touch(c)`（Case を dirty にして予約）と `touchSettings()` に置き換える。どの Case が変わったかを呼ぶ側が渡す。
- 予約は最後の編集から 1 秒後にまとめて送る（打ちながらの書き込みを減らす）。依頼の送付（§4.2）は待たずにすぐ送る。
- 送信：`POST /record/case {id, baseRev, requestId, case}`。時間切れは 20 秒（今の写しと同じ）。送る前に Pending を控えに書く（§3）。
- body の `case.carry` は、送る直前に、その body の Case から計算して入れる（§4.8。`carry.rev` は baseRev＋1）。
- requestId：`crypto.getRandomValues` から作る 32 文字（3-A §4 の形）。

### 4.2 依頼の送付（Q-1）

`deliverOnce` は次の順にする。

0. `canWrite` が偽なら始めない（§2.3。「送る」を押せないように見せる）。設定が clean でなければ、設定の書き込みの 200 を先に待つ（下の 3 の最後の項）。
1. 依頼文を Case に入れる（今と同じ）。
2. その Case の書き込みを**今すぐ**送り、200 を待つ（Pending がもう出ていれば、それを待ってから、依頼文を含む次の書き込みを送る）。
3. 200 のときだけ AI へ送る。200 でなければ送らない。**送らなかったことは Case に書かない**（D-12、再監査の指摘2）：
   - 理由：200 でないとき、その Case は conflict・corrupt・unanswered（offline）・送れない編集（400 など）・控えに書けない（`POST` を出していない）のどれかで、どれも読むだけ（Case を変えられない）。また AI には何も送っていないので、正本に起きたことはない。
   - 代わりに `ui.notSent[id]` に `{ task, at, why }` を入れ、その Case の見出しと帯に「この依頼は送っていません（理由）」と出す。控えに書ければ控えにも残す（読み込み直しても見えるように）。
   - 依頼文は Case の編集（dirty・drafts）として残る。中継に届くようになっても、conflict が解けても、**AI へは自動では送らない**。`canWrite` が真に戻った後、利用者がもう一度「送る」を押したときに 1 から行う。送れたら `notSent` から消す。
   - 今の 004 の `recordDelivery … failed` を Case に書く動きは、3-B ではやめる。
   - 渡し方（`observers`）は設定にある。設定が clean でない（dirty・sending・unanswered・conflict・corrupt）ときは、設定の書き込みが 200 になるまで送らない（§6）。中継が受け取っていない渡し方で送らないため。
4. 送った結果を Case に入れ、ふつうの書き込みとして予約する。

### 4.3 起動と読み込み

`ui.load` は 'loading' で始まる。'loaded' になるまで `canWrite` は偽（§2.3）。読みながら一覧を出すのはよいが、すべて読むだけ。

1. 控えを読む（中継の URL、`currentId`、Pending、drafts）。
2. `GET /record` で一覧（`format` が `ats-record-list-1` でなければ記録の口のない中継とみなし、§5 の「つながらない」と同じ扱い）。一覧が届かない・5xx・503 → 'loadFailed'・offline（3 と同じ）。一覧の `settings.problem` があれば設定は corrupt（§6.1）。
3. `GET /record/settings` と、一覧の全 Case を `GET /record/case` で 1 件ずつ順に読む（D-4。11/4 の写し r536 の 55 件・約 8.8 MB で 1.4 秒。§12。ブラウザからの時間は未確かめ）。
   - 1 件の答えが 409 `record_corrupt`、または一覧に `problem` がある → その Case は corrupt として載せ（§4.5）、読み込みは続ける。設定（`GET /record/settings`）が 409 `record_corrupt` なら設定を corrupt にして続ける（依頼は送れない。§6.1）。設定が届かない・5xx・503 なら Case と同じく 'loadFailed'。
   - 1 件が「届かない・時間切れ・5xx・503」→ `ui.load` を 'loadFailed'、`ui.relay` を offline にして止める。読めた Case は読むだけで出す。届くようになったら `resume()`（§2.3）が **`GET /record` からやり直す**（読めた Case も、新しい一覧の rev・sha256 と違えば読み直す。同じなら読み直さない）。
   - 一覧にあるのに 404 `no_such_case` → 一覧を読んだ後に消えることは 3-A ではないので、不具合として 'loadFailed' にし、やり直す。
4. すべて読めたら `ui.load` を 'loaded' にし、`resume()` を呼ぶ（§2.3。`ui.cache` が failed なら、ここでは送らずに待つ）。
5. `canWrite` が真になったら、控えの Pending を、Case ごと（設定も）に**同じ requestId・同じ body のまま送り直す**。rev を比べて先に決めない（指摘1。3-A は履歴のすべての版から requestId を探すので、書けた後に別の画面がさらに書いていても `replayed` で答える。3-A §3.1-4）。
   - 200（`replayed` を含む）→ 書けていた・または今書けた。その後は §2.4（drafts がなければ clean、あれば答えの `currentRev` で次の書き込みか conflict かを決める。drafts のある Case を中継の版で置き換えない）。
   - 409 `version_conflict` → 書けておらず、その間に別の画面が書いた。conflict（§4.4。自分の編集は drafts にある）。
   - 409 `request_id_reused` → 起きないはず。conflict と同じに扱い、ログに残す。
   - 409 `record_corrupt` → corrupt。
   - 届かない → §2.2（offline）。
   - 一覧にない Case の Pending（新しい Case）は、`baseRev: 0` の同じ Pending を送る。答えの扱いは同じ。
6. Pending がなく drafts（dirty の中身）だけがある Case は、控えの drafts の土台の rev（drafts に `baseRev` として残す）と一覧の rev が同じなら、その rev を baseRev にして送る。違えば conflict（§4.4。別の画面が書いた）。

### 4.4 版がぶつかったとき（conflict）

- その Case は読むだけになり、見出しに「この Case は別の画面で更新されました」を出す。
- 選択肢：「最新を読み直す」（中継の版を読み、自分の編集は控えの drafts に残す）、「自分の編集を JSON で書き出す」。
- 読み直した後、自分の編集を最新に手で足し直す（自動では混ぜない）。drafts は利用者が「控えを捨てる」を押すまで残す。

### 4.5 壊れた Case（corrupt）

- 読む口が 409 `record_corrupt` の Case は、一覧に出し、開くと「中継の記録が壊れています（直し方は README）」だけを出す。画面からは直さない。

### 4.6 JSON の読み込み・新しい Case

- 新しい Case：`baseRev: 0` で書く。200 の後に一覧の順に入れる（作成時刻の新しい順。先頭に来るのは今と同じ）。
- 記録 JSON の読み込み：中継にない Case なら `baseRev: 0`。既にあれば今と同じく「置き換えますか」と聞き、`baseRev` を今の rev にして書く（中身は読み込んだもの。履歴に前の版が残る）。一覧の位置は作成時刻で決まる（今のように先頭には来ない。3-A §2.2 の注意）。
- 写しから戻す（`restoreFromCopy`）：記録の口では使わない（記録全体を置き換える口がないため。3-C）。

### 4.7 他の画面の更新を知る

- 60 秒ごと（今の `checkRecord` の代わり）に `GET /record` を読み、rev の変わった Case のうち clean のものは読み直す。dirty・sending の Case は読み直さない（書き込みの 409 で分かる）。
- 今の「別のスタジオが同じ中継に書いています」の警告は、記録の口では**不要になる**（2 つの画面が同じ正本を版つきで使うため）。代わりに「この Case は別の画面で更新され、読み直しました」を小さく出す。

### 4.8 運び手の向きの見え方（`case.carry`）

ブラウザを持たない運び手（Claude Code・Codex など）は、記録の口を直接読める（`GET /record`・`GET /record/case`）。ただ §12 の実験で、**Case の生の JSON から「どの依頼が返事待ちか」を運び手が自分で判断すると誤る**ことが分かった（貼り付けで取り込んだ返事は `parseAttempts[].expectedTask` が空で、`assignment.task` にしか Task ID がない。画面の `StudioState` の規則を知らないと「返事待ち」と読み違える）。この PC には Node.js もなく、画面の規則を外で動かせない。

そこで、画面が Case を書くたびに、画面の規則で計算した見え方を Case の中に入れる。

```
case.carry = {
  format: 'ats-carry-1', at,                  // 画面が計算した時刻
  rev,                                        // この書き込みが中継で付く rev（baseRev＋1）。古いかどうかの見分けに使う
  stage,                                      // 今の段（STAGES の名前）
  waiting: [{ kind, name, task, gen, sha256, connector, delivery }],   // 返事を待つ今の世代の依頼
  next: '…'                                   // 人が次にすること（画面の表示と同じ文）
}
```

- 計算は `StudioState` だけで行い、画面の表示と同じ関数を使う（2つの規則を作らない）。
- `carry` は**写しの見え方であって正本ではない**。運び手は、依頼文そのものは `case.requests` の本文と `sha256` で確かめる。
- **古いかどうかの見分け（指摘9）**：運び手は `GET /record/case` の答えの `rev` と `case.carry.rev` を比べ、**同じときだけ** `carry` を使う。違う・`carry` がないときは、`carry` を使わず、人に「この Case の見え方は古い（画面で開いて保存し直してください）」と伝える。3-A は Case の中身を調べず、画面以外のプログラムも書けるため、「画面だけが書く」は決まりであって口の保証ではない。`rev` の比べで、画面以外が書いた版を見分けられる。
- 画面は、どの書き込みでも（編集・依頼の送付・JSON の読み込み・書庫から戻す・conflict の後の書き直し）、送る直前にその body から `carry` を計算し直す（§4.1）。送り直しは同じ body なので、`carry` も同じ。
- 中継（3-A）は Case の中身を深く調べないので、中継は変えずに済む。
- 運び手は**記録の口に書かない**（Case を書くのは画面だけ）。返事の取り込みは、課題 4（`_inbox` から画面が取り込む）で別に作る。3-B では README と（課題 6 の）`AGENTS.md` の下書きにこの決まりを書く。

## 5. 中継に届かないとき

- 起動時に届かない：画面は控えの drafts と「中継に届きません。記録は読めず、保存もできません」だけを出す。新しい Case は作れない（`ui.load` は 'loadFailed'）。
- 使っている途中で届かなくなった：Pending は unanswered、`ui.relay` は offline（§2.2）。大きな帯で「中継に届きません。最後に保存できたのは hh:mm。届くようになると自動で送り直します」。
- 境目（指摘3）：**届かないと分かった時点**（`ui.relay` が offline になった時点）から、すべての編集を止める（読むだけ。D-2）。その前にした編集は、送っている途中の編集も含めて Case と控えの drafts にあり、届くようになった後に `resume()` の順（§2.3・§2.4）で送る。offline の間に新しい編集はできないので、「届かない間の編集」は生じない。

## 6. 設定

- ブラウザごとに残す（控え）：`proxyUrl`（記録の口を見つけるのに要る）、`exchangeDir`・`exchangeFor`（その中継から聞いた値）。
- 中継の設定（`/record/settings`）に置く：`observers`（各 AI の渡し方）。どの画面から開いても同じになる。
- この分け方は D-5（§12 の実験で、記録の写しの settings に `proxyUrl` が入っていたことから）。

### 6.1 設定の書き込み（指摘5）

- 設定は Case とは**別の rev** を持つ（3-A：`GET /record` の `settings.rev`、`GET /record/settings` の `{ rev, sha256, settings }`、`POST /record/settings {baseRev, requestId, settings}`。規則は Case と同じで、id は `_settings`）。
- 画面は設定を `meta._settings` で持ち、§2.1 の表と同じ状態（clean・dirty・sending・unanswered・conflict・corrupt）で動かす。`touchSettings()` は設定を dirty にし、Case と同じく 1 秒後にまとめて送る。同時に出る設定の書き込みは最大 1 つ。
- Pending は控えの `pending._settings`、編集の中身は `drafts._settings` に置く（§3 と同じく、書けてから送る）。
- conflict：設定は読むだけになり、「設定が別の画面で更新されました」。選択肢は「最新を読み直す」だけ（自分の編集は drafts に残り、見られる）。自動では混ぜない。
- corrupt（409 `record_corrupt`）：設定は読むだけ。依頼の送付も止める（渡し方を確かめられないため）。
- 依頼の送付は、設定が clean のときだけ（§4.2）。

## 7. 2-C の写し（`/snapshot`）

- 記録の口では、Case ごとの履歴が中継に全部残るので、記録全体の写しは要らなくなる。
- 3-B の画面では写しを送らない（D-3）。写しの口（`/snapshot`）は中継に残す（004 の画面が使う）。

### 7.1 書庫（`/archive`・`/archives`）

書庫は、ブラウザの保存領域の上限（普段の Chrome で 5,242,880 字）から古い Case を逃がすために作った（004）。3-B では Case の本体を保存領域に置かない（§3）ので、書庫へ**移す**理由はなくなる。一方、運用の書庫には既に Case があり、3-C で移す材料にもなるので、**読む・戻す**は扱う。

- **移さない（D-7）**：3-B の画面には「書庫へ移す」を出さない。書庫の口（`POST /archive`）は中継に残す（004 の画面が使う）。
- **一覧は中継から読む（D-8）**：書庫の一覧は `GET /archives` から作る。004 の保存領域の見出し（`store.archived`）は読まない（U-12：3-B の画面は `ats-operational-001` を読まない）。中継のファイル名から Case 番号が分かり、同じ番号のファイルが複数あるときは**一番新しいもの**を使う（004 の画面の「名前のない見出しから戻す」と同じ）。題は、利用者が開いたときに `GET /archive` で読んで出す（一覧のために全ファイルを読まない）。
- **新しさの順（指摘7）**：ファイル名 `<Case>--<時刻>[-<k>].json` を、①時刻（`YYYYMMDDThhmmssmmmZ`、文字列の比べで時刻の順になる）、②同じ時刻の中では `k` を数として比べる（`-k` のないものは k＝1。`-2` は 1 より新しい）で並べる。今の中継（b2fcb01）の `archive_files()` は名前の文字列で並べるため、同じミリ秒の `…Z.json` が `…Z-2.json` より新しいと誤る（Claude Code が 11/8 に再現。004 の「名前のない見出しから戻す」にも同じ誤りがある。同じ Case を同じミリ秒に 2 回移すことはふつう起きない）。**中継の並べ方を上の順に直し**（D-10 ①）、画面も同じ順で選ぶ（中継の順に頼らない）。
- **書庫の状態（指摘6）**：今の `GET /archives` は、書庫のフォルダがないときも、シンボリックリンクのときも、200 の空の一覧を返し、見分けられない。**中継を直し**（D-10 ②）、答えに `folder: 'present' | 'absent'` を足し、フォルダがリンク・フォルダでない・読めないときは 409 `{ error }` を返す（`POST /archive` がリンクのとき 409 を返すのと同じ）。`absent` は「書庫がまだない（移した Case がない）」で、正常。3-B の画面は、`folder` のない答え（直す前の中継）を「書庫を読めない」とみなす。
- **戻す**：`GET /archive` で読み、`sha256` が答えの本文と一致し、`ats-operational-case`（version 1）として読め、Case 番号がファイル名と同じときだけ、§4.6 の JSON の読み込みと同じ道で記録の口に書く（中継になければ `baseRev: 0`、あれば「置き換えますか」）。書庫のファイルは消さない（中継にも消す口がない）。戻した後も書庫の一覧には残り、「記録の口にあります」と添える。
- **Case 番号（指摘8、D-11）**：新しい Case の番号は、作る直前に読んだ `GET /record` の一覧と `GET /archives` の両方にある番号を**避けるよう努める**（004 の `knownCaseIds` と同じ考え）。`GET /archives` が読めない（409・届かない・`folder` がない）ときは新しい Case を作らない。
  - 保証の範囲：記録の口の中の重なりは 3-A が防ぐ（同じ番号を `baseRev: 0` で書くと 409）。**書庫との重なりは防げない**：書庫の口は記録の口のロックの外にあり、一覧を読んだ後に別の画面（004）が同じ番号を書庫へ移すことがありうる（今の口では原子的に防げない）。新しい番号には日付と 3 桁の連番に加え、いつも 6 字の乱数が付く（`StudioText.caseIdFor`。2-B 以降）ので、番号がまるごと同じになるのは、004 と 3-B を同じ中継で同時に使い、同じ日の同じ連番を作り、乱数まで一致したとき（36 の 6 乗分の 1）に限られる。連番だけが同じで乱数の違う 2 つの Case は、番号の重なりではない（別の Case として両方残る。表示の連番が重なって見えるだけ）。乱数のない古い番号（`CASE-YYYYMMDD-NNN`）は新しく作られない（`caseIdFor` は乱数が 6 字に満たなければ番号を作らない）。
  - 起きにくくする決まり：3-C（移行）までは、3-B の画面は**試験用の中継**（8797）だけで使い、運用の中継（004 が書庫に移す中継）には向けない。
  - 起きたら止める：書庫の一覧と記録の口に同じ番号があれば、その番号の書庫のファイルに「記録の口に同じ番号の Case があります（別の Case かもしれません）」と出す。戻すときは必ず「置き換えますか」を経て、置き換える前に両方の題・作成時刻を並べて見せる。黙って置き換えない。
- **運び手**：書庫は読むだけ。書庫のファイルには `case.carry`（§4.8）がない（004 の画面が書いたため）。書庫の Case は古いものなので、運び手は書庫から返事待ちを判断しない。
- **3-C（移行）で決めること**：書庫の Case を記録の口に入れるか、書庫に置いたままにするか。入れるなら、004 の `store.archived` の見出し（`name`・`sha256`）と `_archive` のファイルを照合してから入れる。Claude Code の推奨は「入れる」（正本を 1 か所にし、運び手が 2 か所を探さずに済む。保存領域の上限は記録の口では関わらない）。決めるのは利用者。

## 16. 実装で足したこと（0.6 の後、2026-11-08、Claude Code。未監査）

実装（`studio_record.js`・`app.js`）と結合試験の中で、契約に書いていなかった次の決まりを足した。次の監査で見てもらう。

1. **送っている途中の書き込みを待つ**：`saveNow`（Q-1）と `flush` は、同じ Case の書き込みが中継へ出ている間は、その答えを待ってから進む（1 つの Case に同時に出る書き込みは 1 つのまま）。結合試験で、Case を作った直後の自動送付が「送っている途中」を理由に止まった（安全側だが、毎回人の操作が要る）ことから足した。U-04 に試験を足した。
2. **読み直す前の古い中身では書かない**：部品が渡した Case の中身は、読み直し（他の画面の更新・conflict の「最新を読み直す」）のたびに新しい物になる。画面が時間のかかる処理（AI への送付・資料の確かめ・回収）の途中で持っていた**古い物**で `save(c)` しても、部品は書かず、その中身を「自分の編集」（`mine`、§4.4 と同じ控え）として残す。古い物で書くと、他の画面の更新を黙って上書きするため。JSON の読み込みで置き換えるとき（`replaceCase`）は除く。部品は渡した物ごとにどの版のものかを覚えて見分ける（新しく作った物は、その時点の版として受ける）。試験を足した。
3. **送れない編集の状態の名前**：400・413・415 の答え（§2.1 の「送れない編集。止める」）の状態を `refused` とした。
4. **画面の作り直し**：部品の変化のたびに全体を作り直すと、判断の理由などを打っている途中の文字が消えるため、記録の状態・開いている Case・その状態・一覧が変わったとき、または開いている Case が読み直されたときだけ全体を作り直す（それ以外は左の表示と帯だけ）。
5. **初期設定は渡し方だけ**：中継の `studio.config.json` から読むのは各 AI の渡し方だけで、中継の URL は読まない（D-5。試験用の中継で開いた画面が運用の中継を指さないため）。
6. **（実装の監査の後）Q-1 は依頼文を入れたその物で確かめる**：`saveNow(id, value)` は、`value`（画面が依頼文を入れた Case の物）が部品の今の物と同じで、その中身が中継から 200 を得たときだけ ok。読み直しで古くなった物は ok にならない（6 の前は、今の Case が clean なら ok になり、古い物にだけある依頼文を保存せずに送りえた。監査の指摘1）。画面は `save(c)` が断られたら送らない。
7. **（実装の監査の後）設定の読み込み**：`GET /record/settings` が 200 でも 409 `record_corrupt` でもないとき、読み込みは 'loadFailed'（書けない）。監査の指摘2。
8. **（実装の監査の後）書庫から戻す**：SHA-256 を計算できないブラウザでは戻さない（照合できないため）。監査の指摘3。
