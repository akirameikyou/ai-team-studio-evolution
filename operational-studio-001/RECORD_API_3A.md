## 1. 守ること（統合で挙がった最大の危険への答え）

1. **Case のファイルが正本**。一覧（index）は Case のファイルから作り直せる「索引」に留め、一覧と Case が食い違ったら Case のファイルを正とする。複数のファイルを1回で原子的に書く必要をなくす。
2. **書き込みは中継の中で1つずつ**（記録全体に1つのロック）。中継は記録のフォルダごとに1つだけ動く（2つ目は起動時に止まる。§6）。
3. **版が合わなければ書かない**（409）。自動で混ぜない。
4. **途中で失敗しても、書き始める前の状態か、書き終えた状態のどちらかしか残らない**。消さない。
5. **公開ページからは使えない**（今の写しの口と同じ）。

## 2. ファイルの置き場所と形

置き場所：`proxy/exchange/_record/`（`proxy/exchange/` は Git の対象外）。

```
_record/
  .lock                       中継が使用中の印（§6）
  settings.json               設定（中継URL・各AIの渡し方）と、その版
  cases/<Case番号>.json        Case 1件の正本
  history/<Case番号>/<rev>.json 書き換える前の版（消さない）
```

`cases/<Case番号>.json`：

```json
{ "format": "ats-case-1", "id": "CASE-20261025-002-s1rcia", "rev": 12,
  "savedAt": "2026-10-25T05:00:00.000Z", "requestId": "…", "sha256": "<case の JSON の SHA-256>",
  "case": { …今の store.cases[id] と同じ形… } }
```

- `rev` は Case ごとの版（1 から）。記録全体の rev（今の `store.rev`）とは別。
- `sha256` は `case` を中継が決まった形（UTF-8・キー順そのまま・`ensure_ascii=False`・区切り `,` `:`）で書き出した文字列のもの。
- Case の一覧の順（今の `store.order`）は、各 Case の `createdAt` の新しい順で作る。順を別のファイルに持たない（食い違いの種を減らす）。10/25 の写し r464（47 件）で、全 Case に `createdAt` があり、`store.order` がこの順と一致することを確かめた。
- 今どの Case を開いているか（今の `store.currentId`）はブラウザごとの画面の状態なので、中継に置かない（3-B で localStorage に残す）。

## 3. 口（API）

すべて JSON。Origin の扱いは §5。大きさの上限は §4。

| 口 | 中身 | 答え |
|---|---|---|
| `GET /record` | 一覧 | `{ format, cases: [{ id, rev, sha256, bytes, createdAt, title }], settings: { rev }, history: { files, bytes } }`。`title` は問いの1行目（先頭 80 字） |
| `GET /record/case?id=` | Case 1件 | `{ id, rev, sha256, case }`。なければ 404 |
| `POST /record/case` | Case 1件を書く。`{ id, baseRev, requestId, case }` | 200 `{ id, rev, sha256 }`。§3.1 |
| `GET /record/settings` | 設定 | `{ rev, settings }` |
| `POST /record/settings` | 設定を書く。`{ baseRev, requestId, settings }` | Case と同じ規則 |

削除の口は作らない（3-A の範囲外。必要になったら別に決める）。移行用の口（記録全体を一度に入れる）は 3-C で決める。

### 3.1 書き込みの規則（POST /record/case）

1. 形を確かめる（§4）。だめなら 400／413。何も書かない。
2. 記録全体のロックを取る。
3. 今のファイルを読む（なければ rev 0）。
4. **同じ `requestId` の書き込みが既に済んでいて、`case` の sha256 も同じ**なら、何も書かずに 200（前の答えと同じ `rev`）。書けたのに答えが届かなかった場合の送り直しで、重複も消失も起きないようにする。同じ `requestId` で中身が違えば 409。
5. `baseRev` が今の rev と違えば **409** `{ error, currentRev, currentSha256 }`。何も書かない。
   - 新しい Case は `baseRev: 0`。既にあれば 409。
6. 今のファイルがあれば、`history/<id>/<今のrev>.json` に**そのまま**写す（write_atomic）。既に同じ名前があれば中身を比べ、同じなら進む、違えば 500 で止める。
7. 新しいファイル（rev＋1）を `cases/<id>.json` に write_atomic で書く。
8. ロックを放して 200。

途中で止まった場合：6 の後で止まれば、履歴に同じ版が1つ余分にあるだけで、正本は前の版のまま（送り直しで 6 は「同じなら進む」）。7 は1ファイルの置き換えなので、前か後のどちらか。

## 4. 確かめる形と大きさ

- Case 番号：`^CASE-\d{8}-\d{3}(-[a-z0-9]{6})?$`（旧形式も通す）。`case.id` と一致すること。
- `case` は JSON のオブジェクト。中身の項目は 3-A では深く調べない（今の記録の形をそのまま入れる。未知の項目も残す）。
- `requestId`：英数字と `-`、8〜64 字。
- 1回の書き込みの大きさ：**2 MiB まで**（今の最大の Case は約 400 KB）。超えたら 413。※値は要判断（§8）。
- `baseRev`：0 以上の整数。

## 5. 使えるページ（アクセスの規則）

- 今の写しの口と同じく、**Origin が localhost／127.0.0.1 のページ、または Origin なし**だけに答える。GitHub Pages の Origin には 403。
- 加えて、**Host ヘッダーが `127.0.0.1:<port>` か `localhost:<port>` のときだけ**答える（外の名前を手元に向ける攻撃への備え）。
- Origin なし（試験・ローカルの道具・将来のブラウザを持たない運び手）を認めるかは要判断（§8）。認める場合も、中継は 127.0.0.1 だけで待ち受けるので、届くのはこの PC の中のプログラムに限られる。

## 6. 中継が2つ動かないようにする

- 起動時に `_record/.lock` を排他作成（中にプロセス番号と起動時刻）。既にあり、そのプロセスが生きていれば起動を止める。死んでいれば印を書き直して起動し、ログに残す。
- 終了時に消す。

## 8. 利用者が決めたこと（2026-10-25、4点とも推奨どおり）

1. 履歴の保持：3-A では**消さずに全部残し、件数と合計の大きさを一覧に出す**（推奨）。消す規則は大きさを見てから決める。
2. 1回の書き込みの上限：**2 MiB**（推奨。最大の Case の約5倍）。
3. Origin なしのアクセス：**認める**（推奨。試験・道具・将来の運び手のため。127.0.0.1 だけで待ち受けるので届くのはこの PC の中だけ）。
4. 版がぶつかったときの画面の選択肢（3-B の話）：「最新を読み直し、自分の編集を控えから見ながらやり直す」だけにし、強制上書きは置かない（推奨）。
