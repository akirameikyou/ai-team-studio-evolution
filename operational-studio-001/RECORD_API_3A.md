## 1. 守ること

1. **Case のファイルが正本**。一覧は Case のファイルから毎回作る（一覧のファイルを持たない）。3-A には、2つ以上の正本（Case と Case、Case と設定）を1回で書き換える操作がない。
2. **記録の口はすべて中継の中で1つずつ**（読む口も書く口も、記録全体に1つのロック。§6）。
3. **版が合わなければ書かない**（409）。自動で混ぜない。
4. **読んだ正本は毎回確かめる**。壊れていれば、その Case には書かない（§3.3）。
5. **書いた版は消さない**（履歴は全部残す。利用者の決定 §8-1）。送り直しの判定にも履歴を使う。
6. **この PC のページと道具だけが使える**（§5）。
7. **中継は記録のフォルダごとに1つだけ**（OS のファイルロック。§6.2）。

## 2. ファイルの置き場所と形

置き場所：`proxy/exchange/_record/`（`proxy/exchange/` は Git の対象外）。

```
_record/
  .lock                          中継が使用中の印（OS のファイルロックを掛ける。§6.2）
  settings.json                  設定の正本
  cases/<Case番号>.json           Case 1件の正本
  history/<Case番号>/<rev>.json   書き換える前の版（消さない）
  history/_settings/<rev>.json   設定の書き換える前の版
```

`cases/<Case番号>.json`（版のファイル。履歴のファイルも同じ形）：

```json
{ "format": "ats-case-1", "id": "CASE-20261025-002-s1rcia", "rev": 12,
  "savedAt": "2026-10-25T05:00:00.000Z", "requestId": "…", "sha256": "…",
  "case": { …今の store.cases[id] と同じ形… } }
```

`settings.json` も同じ形で、`format` が `ats-settings-1`、`id` が `_settings`、本体が `settings`。

### 2.1 sha256 の決まり（指摘4）

- 中継が受け取った JSON を、次の規則で読む：数値の NaN・Infinity・-Infinity は断る／同じオブジェクトの中で同じキーが2回出たら断る／UTF-8 にできない文字（対になっていないサロゲート）を含めば断る。どれも 400。
- 読めた `case` を、中継が `json.dumps(case, ensure_ascii=False, separators=(',', ':'), allow_nan=False)` で書き直した**文字列の UTF-8 のバイト列**を「正規の形」とする。キーの順は受け取った順のまま（並べ替えない）。
- `sha256` は正規の形の SHA-256（16進・小文字）。計算するのは中継だけ。画面や道具は自分で計算せず、中継が返した値を比べる。
- 版のファイルを読むときも、`case` を同じ規則で書き直して sha256 を計算し直し、ファイルの `sha256` と比べる（§3.3）。

### 2.2 一覧の順（指摘5）

- `GET /record` の順は、`case.createdAt` を世界標準時の時刻として読んだ値の新しい順。同じ時刻なら Case 番号の文字列の大きい順。
- `createdAt` がない・`YYYY-MM-DDTHH:MM:SS(.sss)Z` の形でない Case は、書き込みの時点で断る（400）。
- 10/25 の写し r464（47 件）で、全 Case に `createdAt` があり、今の `store.order` がこの順と一致することを Claude Code が確かめた（監査では未確認。R-11 で試験にする）。
- 注意：今の画面は「JSON から読み込んだ Case」を一覧の先頭に置く（`store.order.unshift`）。中継の一覧では作成時刻の位置に並ぶ。3-B で画面に伝える（§9）。
- 今どの Case を開いているか（今の `store.currentId`）はブラウザごとの画面の状態なので、中継に置かない。

## 3. 口（API）

| 口 | 中身 | 答え |
|---|---|---|
| `GET /record` | 一覧 | `{ format, cases: [{ id, rev, sha256, bytes, createdAt, title, problem? }], settings: { rev, problem? }, history: { files, bytes } }`。`title` は問いの1行目（先頭 80 字）。壊れた Case は `problem` 付きで載せる |
| `GET /record/case?id=` | Case 1件 | `{ id, rev, sha256, case }`。ない 404・壊れている 409（`record_corrupt`） |
| `POST /record/case` | Case 1件を書く。`{ id, baseRev, requestId, case }` | 200 `{ id, rev, sha256, replayed }`。§3.1 |
| `GET /record/settings` | 設定 | `{ rev, sha256, settings }` |
| `POST /record/settings` | 設定を書く。`{ baseRev, requestId, settings }` | Case と同じ規則（id は `_settings`） |

- 削除の口は作らない。記録全体を一度に入れる口（移行）は 3-C で決める。
- POST は `Content-Type: application/json` のときだけ受ける（ほかは 415）。

### 3.1 書き込みの規則（Case と設定で共通）

1. 形を確かめる（§4）。だめなら 400／413／415。何も書かない。
2. 記録のロックを取る（§6.1。取れなければ 503）。
3. 今の正本を読み、確かめる（§3.3）。壊れていれば 409 `record_corrupt` で止める。なければ rev 0。
4. **送り直しの判定**（指摘1）：今の正本と、その Case の履歴のすべての版から、同じ `requestId` を探す。
   - 見つかり、その版の `sha256` が今回の `case` の sha256 と同じ → 何も書かずに 200（`rev` はその版の rev、`replayed: true`、`currentRev` に今の rev）。書けたのに答えが届かず、その後に別の書き込みがあった場合も同じ答えになる。
   - 見つかり、sha256 が違う → 409 `request_id_reused`。何も書かない。
   - 履歴は消さない（§8-1）ので、中継を再起動しても判定は変わらない。`requestId` の重複は Case ごと（設定は設定の中）で見る。
5. `baseRev` が今の rev と違えば 409 `version_conflict` `{ currentRev, currentSha256 }`。何も書かない。新しい Case は `baseRev: 0`。既にあれば 409。
6. 今の正本があれば、それを `history/<id>/<今のrev>.json` に**バイト列のまま**写す（write_atomic）。同じ名前が既にあれば、バイト列を比べ、同じなら進む、違えば 500 `history_mismatch` で止める。
7. 新しい版（rev＋1、`requestId`、`sha256`、`savedAt`）を `cases/<id>.json` に write_atomic で書く。
8. ロックを放して 200（`replayed: false`）。

### 3.2 途中で止まったときに残るもの（指摘3）

保証は3つに分けて書く。

| 場面 | 保証 |
|---|---|
| 答え（API から見える状態） | 200 を返した書き込みは正本に入っている。200 以外を返した書き込みは、正本を変えていない（6 の履歴だけが残ることはある。下を参照） |
| 中継のプロセスが止まった（強制終了を含む） | 正本は1ファイルの置き換え（os.replace）なので、前の版か新しい版のどちらか。半分書けたファイルは残らない。6 と 7 の間で止まると、**今の正本と同じ中身の履歴が1つ**残る（`history/<id>/<今のrev>.json`）。これは「孤立した履歴」として正しい状態とみなす（送り直しでは 6 の「同じなら進む」で通る） |
| OS の停止・電源断 | 一時ファイルは fsync してから置き換えるが、フォルダの書き込みの確定までは保証しない。止まる直前の書き込みが前の版に戻ることはありうる。半分書けた正本は残らない（書きかけの一時ファイルが残ることはあるが、名前が違い〔`.` で始まり `.tmp` で終わる〕、正本としても履歴としても読まれない） |

3-A には、2つ以上の正本をまとめて書き換える操作はない（Case と設定は別々の書き込みで、それぞれが上の保証を持つ）。

### 3.3 読んだ正本を確かめる（指摘2）

正本・履歴の版のファイルを読むたびに、次を確かめる。1つでも合わなければ「壊れている」。

- JSON として §2.1 の規則で読める
- `format` が決まった値／`id` がファイル名と `case.id`（設定は `_settings`）に一致／`rev` が1以上の整数で、履歴ならファイル名の数字と一致
- `sha256` が、`case` を §2.1 で計算し直した値と一致

壊れていたら：その Case への書き込みは 409 `record_corrupt` で断る。読む口は 409 で、一覧には `problem: "corrupt"` を付けて載せる。中継は自動で直さない。直し方（人が履歴の版から戻す）は 3-A の README に書く。

## 4. 確かめる形と大きさ

- Case 番号：`^CASE-\d{8}-\d{3}(-[a-z0-9]{6})?$`（旧形式も通す）。`case.id` と一致すること。ファイル名に使う前に、この形であることを必ず確かめる（パスの部品にならない）。
- `case` は JSON のオブジェクト。中身の項目は 3-A では `id` と `createdAt`（§2.2）のほかは深く調べない（今の記録の形をそのまま入れる。未知の項目も残す）。
- `requestId`：`^[A-Za-z0-9-]{8,64}$`。
- 1回の書き込みの大きさ：2 MiB まで（利用者の決定 §8-2）。超えたら 413（本文を読む前に Content-Length で判断）。
- `baseRev`：0 以上の整数（真偽値は不可）。

## 5. 使えるページと道具（アクセスの規則。指摘6）

`/record` で始まるすべての口（`OPTIONS` を含む）で、振り分けの**前**に共通の関門を通す。関門で断るときは 403 で、CORS のヘッダーを付けない。

1. **Host**：ヘッダーがちょうど1つで、値が `127.0.0.1:<待ち受けのポート>` か `localhost:<待ち受けのポート>` に一致（大文字小文字は区別しない）。ない・2つ以上・別の名前・別のポート・ポートなしは断る。
2. **Origin**：
   - ない → 認める（利用者の決定 §8-3。試験・道具・将来のブラウザを持たない運び手。中継は 127.0.0.1 だけで待ち受けるので、届くのはこの PC の中のプログラムに限られる）。
   - ちょうど1つで、`^https?://(127\.0\.0\.1|localhost)(:\d+)?$` に完全一致 → 認める。
   - それ以外（GitHub Pages を含む別の住所・`null`・2つ以上）→ 断る。
3. POST は `Content-Type: application/json` だけ（§3）。別の住所のページからは、ブラウザが必ず事前の確認（OPTIONS）を送るので、1・2 で止まる。

今の写しの口（`/snapshots`・`/snapshot`）には Host の確認がない。同じ関門を掛けるかは 3-A の範囲外とし、別に決める（LIMITATIONS に記す）。

## 6. ロックと二重起動

### 6.1 中継の中のロック（指摘8）

- `/record` の口はすべて、記録全体に1つのロック（threading.Lock）を取ってから処理し、`finally` で必ず放す。読む口も対象（一覧は複数のファイルを読むため）。
- ロックを待つのは最大 10 秒。取れなければ 503 `busy`。
- 待っている間に相手が切断しても、ロックを取った後の処理は最後まで行う（書き込みは §3.2 の保証どおり）。答えを書けなかったことはログに残す。
- 写しの口・観測の受け渡しの口はこのロックを取らない（記録の口の遅れが他を止めない）。

### 6.2 中継の二重起動（指摘7）

- 起動時に `_record/.lock` を開き、**OS のファイルロック**（Windows は `msvcrt.locking(…, LK_NBLCK, 1)`、ほかは `fcntl.flock(LOCK_EX | LOCK_NB)`）を掛ける。掛けられなければ「別の中継が同じ記録を使っています」と出して起動を止める。
- ロックはファイルを開いている間ずっと持ち、プロセスが終われば（強制終了でも）OS が外す。プロセス番号では判断しない（番号の使い回しに左右されない）。
- `.lock` の中身（プロセス番号・起動時刻）は人が見るための情報で、判断には使わない。終了時にファイルは消さない（消す・作るの競合を作らない）。

## 9. 3-B で決めること（3-A の範囲外。指摘10）

- 画面の保存を、記録全体から「Case ごと・設定ごと」の書き込みに分ける。Case ごとの rev と設定の rev を画面が持つ。
- 今の `store.rev`（記録全体の版）と写しの名前の rev をどうするか。
- `currentId` はブラウザの保存領域に残す。
- 一覧の順は中継の順に従う（JSON から読み込んだ Case が先頭に来なくなる）。
- 未送信の編集の控え（中継が止まっている間・版がぶつかった後）と、読み直した最新の版との結び直し。
- 答えが届かなかったときの送り直し（同じ requestId を使う）。
- 中継が止まっているときは読むだけにし、保存できないことを大きく出す。
